Where leaks come from

One agent booking a trip for a user, drawn as a data-flow graph. Give it capabilities, add defenses, and watch which edges can carry what to whom.
The idea — A leak is not a bug in one place. It is a path: data the agent can reach, an input that can steer it, and an edge out to someone who should not get it. Every capability adds edges. Every defense cuts a path at one specific point, and the report's open problems are the paths no single cut closes. Red edges sit on an open attack path, amber on a mitigated one. Pick a path in the list to trace it.

How to read it

Three things fall out of playing with the graph. First, the dangerous capabilities are the ones that put untrusted text and an outbound channel in the same context: browsing alone is both, which is why the report treats a malicious environment as its own threat model (§3.2). Second, defenses work at different places. Minimization shrinks what the agent holds; untrusted-input handling stops text from steering it; a contextual flow check judges each edge out; scoped credentials shrink what any hijack can do. Each one closes some paths and leaves others. Third, with every defense on, one path stays open: two flows that each pass every check, combined by one observer (OP 11.5). That is not a missing toggle; it is the report's point that per-flow appropriateness has no composition rule yet.

The graph is a teaching model, not a threat model of any real product. Statuses are curated from the report's framing, and the honest version of every "closed" is "closed if the defense works as designed", which the report repeatedly says today's systems do not guarantee. For the patterns behind each toggle, see For builders.
