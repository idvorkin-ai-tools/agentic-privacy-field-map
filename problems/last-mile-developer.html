AI as the last-mile developer

What makes an application agentic, and why the answer is also the security problem
Source§7.5 What makes an application agentic, and what does this mean for security?, pp. 39–44 ↗
TL;DR — An agent is ordinary software in which some of the code is written by a model at run time. The more of the program the developer hands to the model, the more "agentic" the app is, and the less the developer's own code constrains what can happen. The report makes this concrete with a thought experiment: replace every LLM call with an arbitrary choice and read what is left. An email-to-calendar app still only ever creates a calendar event; a general planner becomes exec(*). OP 7.10 asks how to close the gap between what the developer meant and what the program permits; OP 7.11 asks how to bring testing, review and red-teaming back to code that is generated and run in the same breath.

Section 7 of the report is about system-level guardrails: identity, authorization, data minimization, and the machinery around the model rather than inside it. Section 7.5 steps back and asks the prior question (p. 39). If an agent is just a program that calls a function named llm(), why do we need new security ideas at all? The report's answer is that the novelty is not the model call itself but how much of the program's control flow and specification the model is allowed to decide. This is the executive summary's "probabilistic, dynamic control flows" dimension, worked through with code. It is also the most programmer-friendly part of the report: you can reason about it the way you reason about any untrusted input.

The agentic spectrum, in two programs

The report frames "agentic-ness" as how much application development the developer offloads to the model (§7.5.1). At one end, the model is a natural-language parser that pulls fields out of an email. At the other, it discovers, writes and runs new code. In a traditional app the developer enumerates every workflow by hand ("add to cart, set quantity, check out"). In an agentic app, the developer lets the model assemble a workflow for a request nobody anticipated, such as reading colleagues' emails and scheduling the meetings they mention. That is the payoff: functionality that would be too expensive to build by hand. The report points to existing definitions of agentic levels for this spectrum, citing Mitchell et al. (2025).

Two running examples anchor the rest of the section (p. 40):

email-to-calendar-eventTakes an email, asks the model whether it is a scheduling request, and if so asks it for date, time and location. Then it calls one hard-coded tool: calendar.create_event. The model decides which branch to take and fills in parameters. It cannot pick a different tool.
general plannerTakes a natural-language request and loops: ask the model for the next function to call, execute it, append the output to the context, repeat until the model says "DONE". The model is writing the program one step at a time.

The report gives both in C++-flavored pseudocode. Here is a shortened version of each. This is our simplification of the report's listings, not a copy.

// email-to-calendar (simplified from the report's pseudocode)
bool from_email(email) {
  if (llm("is this a scheduling request? " + email)) {
    (date, time, place) = llm("extract date, time, place: " + email);
    return calendar.create_event(date, time, place);   // fixed tool
  }
  return false;
}

// general planner (simplified)
void handle(request) {
  ctx = SYSTEM_PROMPT + request;
  loop {
    step = llm(ctx);                // model picks the next call
    if (step == "DONE") break;
    out  = exec(step);              // whatever it picked, run it
    ctx += step + out;              // state now depends on model output
  }
}

Both programs "use AI". The difference is what the developer still owns. In the first, the developer owns the control flow and the set of possible side effects; the model only chooses among them. In the second, the developer owns a loop and an exec.

What goes wrong when the model finishes the code

Section 7.5.2 names two consequences of delegation (p. 40). The first is a mismatch between intent and behavior. A model's only real specification is "tokens in, tokens out", so it has no formal constraints that rule out errors. The report's example: the calendar app's model might consistently read dates backward. That is a perfectly valid token transformation and a failure of the developer's intent at the same time. Nothing in the program says it is wrong.

The second is timing. Code written by a person goes through iteration and review, usually away from adversaries, before it runs. A workflow the model generates for a user request is expected to run almost immediately, with little or no human involvement, and often while reading attacker-controlled content. Those two observations become the two open problems.

OP 7.10 · Closing the gap between developer intent and application specification

In plain terms: when part of an application is generated by a model, the set of things the program can do grows beyond what the developer meant it to do, and beyond what users expect. How do we shrink that gap (§7.5.2, p. 41)?

In a traditional app, intent and specification line up (bugs aside). Users press buttons or type exact commands that are parsed deterministically, so the structure of the input already limits what can happen. An agentic app deliberately drops that structure so it can handle unstructured requests. The developer gains features that would be tedious or infeasible to write by hand. The user gains flexibility. And the specification now admits executions nobody intended.

The developer's two bad options

The report lays out the choice the developer is stuck with:

1 · Limit functionalityConstrain what form user input can take and define by hand what happens for each input. Safe, and back to traditional software.
2 · Accept unintended executionsLet a model interpret the input and choose what to run, and accept that some of what it runs will be unexpected or destructive.

Applied to the examples: for the calendar app, unless the developer restricts the input format, there is no static boundary around create_event other than trusting the model to be right. For the planner, the developer's intent is "do whatever the user wants", so which actions are appropriate is only knowable after the request arrives. To support unconstrained requests, every possible action has to be statically allowed.

Trusting the model to translate input into a precise execution is complicated, in the report's framing, by two things: models cannot reliably reason about ambiguous, unpredictable requests (and we cannot inspect why they decide what they decide), and models can confuse trusted instructions with untrusted content such as a prompt injection, which then rewrites the application's effective specification.

The havoc argument: replace the LLM with *

This is the section's central move, and it is worth internalizing. Take each program and replace every LLM call with a nondeterministic operator, written *. The report notes this is akin to "havoc" in programming-language semantics: the value can be anything. That models a model that interprets input in any possible way, including while an adversary is steering it (pp. 41–42). Then ask what the remaining code still guarantees.

// email-to-calendar with every llm() replaced by *  (simplified)
bool from_email(email) {
  if (*) return calendar.create_event(*);
  return false;
}

Even with a fully adversarial model, this program can do exactly two things: return false, or create some calendar event. The developer statically downscoped the app to "calendar events from email". You can enumerate the failure modes (a missed event, a bogus event) and decide whether they are tolerable. The report calls the consequences of a wrong branch "tractable".

// general planner with every llm() replaced by *  (simplified)
void handle(request) {
  loop {
    if (* == "DONE") break;
    exec(*);
  }
}

Here the residue is exec(*) in a loop. There are no static boundaries left; nearly the whole specification belongs to the model. Anything the runtime can do, this program can do.

"the larger the portion of the application delegated to AI, the more utility and flexibility the application can offer. . . and the more risk the application poses to its users should the AI misbehave."— the report, §7.5.2, p. 42

A way to picture this: the havoc version is the program's security perimeter. Whatever the model does, it cannot get outside what the havoc version allows. For the calendar app that perimeter is one tool call. For the planner it is everything the process has permission to do. Our reading is that this gives builders a cheap design-time test: write the havoc version of your agent and see whether you can live with every execution it permits.

The report then poses the harder questions: can the gap be closed at all, can correct or safe behavior be "guaranteed", and how would "correct" even be defined if not by a developer writing down a precise description, which may be infeasible or would just put us back in traditional code?

Three directions the report proposes

These are framed as questions to explore, not results (pp. 42–43).

1. Security monitors for contextual correctness. Traditional systems use security monitors, such as sandboxes, that enforce input and output policies based on signals from the application and environment. What does a monitor look like when "secure" depends on social context and unstructured, dynamic inputs? The strawman is the user as monitor, confirming every action; the report notes user confirmation is a common fallback for agents today. Prior work it cites (AirGapAgent, Conseca, CaMeL, f-secure LLM systems, Sapien, IsolateGPT) instead uses trusted, isolated models to generate monitors expressed in a policy language or in code, as a scalable stand-in for what a human security expert would write. The open question is whether any monitor can both reduce the human burden and give stronger guarantees than those model-generated monitors, and whether hard guarantees are possible at all when the specification itself contains model-generated, contextual execution.

2. How much agentic-ness do we actually need? Could existing agentic apps get the same functionality with more precision by paying for more manual specification? For example, a tighter calendar workflow that reduces parsing mistakes while still delivering "event from email". More generally, can agentic apps be written in a more traditional shape, using the model only for narrow purposes rather than full planning? And for which apps is that impossible, and why?

3. What does each form buy you? The same app can be built at different agentic levels. What does each version offer for functionality, security, or ease of building? Why do we trust a traditional implementation differently from one that routes through a model call, and can that distinction be stated formally?

A good answer to OP 7.10 would have to do something neither bad option does: keep most of the flexibility of option 2 while giving the developer a static, checkable bound on what can happen, the way the calendar app's havoc version does, without requiring the developer to enumerate every workflow by hand.

The parallel with untrusted, dynamically loaded code

The report adds a note that makes the problem feel less exotic (p. 43). Letting an LLM "define" part of an application is like any traditional program that loads code or binaries at run time with complex or unknown control flow. We already handle that with sandboxes and VMs.

The web browser is the standing example. It fetches JavaScript from many sources at run time, so it cannot vet dependencies ahead of time the way a static build can. Instead it isolates sites: it sandboxes page rendering, enforces permissions, and maintains the Same-Origin Policy, so a script loaded on one site cannot read another site's data.

The catch is who sets the boundary. In those systems the developer decides statically which limited permissions the sandbox grants, and traditional apps have accepted that restriction. In the agentic world, the report observes, static restrictions are seen as too much friction or too great a cost to utility, which leaves new and perhaps more dynamic security mechanisms as the remaining path. Our reading: the browser shows that running untrusted code safely is a solved shape of problem, but only once you agree on a fixed perimeter. Agents are hard because the perimeter is supposed to move with the task. That is the bridge to the report's notion of contextual security in §5.

OP 7.11 · Making agent execution as robust as traditional software

The question: software development practice is a big part of why ordinary software is reliable and secure. How do we bring that practice back when the "software" is a workflow the agent generated a moment ago (p. 43)?

Why it is hard for agents specifically: the same expectation that makes agents attractive, that they generate new workflows on the fly, comes with the expectation that they act quickly and on their own. That rules out the programmer in the loop and squeezes out design exploration, iteration, testing, evaluation and red-teaming. And the need for those processes scales with agentic level. The calendar agent's limited agency already bounds what a "rogue LLM result" can do, so little extra review is needed to check its choice of event. Verifying an arbitrary execution produced by a general planner would need far more.

"How can we bring back software development processes to agentic execution to ensure robustness?"— the report, OP 7.11, p. 43

Four considerations

The report lists these as open considerations (pp. 43–44):

1 · Just-in-time product managementProduct management is the process that pins down what the customer actually needs. Can an agent do a fast, in-the-moment version of it, for example by asking the user to resolve ambiguity when it generates a workflow for their request?
2 · Security validationIf an application can take the form of AI-generated code, which existing validation tools apply? The report lists formal verification and proof systems, approximate path exploration such as fuzzing and static analysis, and red-teaming and pentesting. All of them need a precise specification of what counts as a vulnerability, such as formal invariants. So who is trusted to write that specification? Possibly a trusted security monitor of the kind described under OP 7.10.
3 · Cost and who does itWhat time and resources would reintroducing these processes take? Do humans have to be in the loop, or could a "code review" or "formal verification" model do a sufficient job?
4 · Vetted artifactsIs an agentic app that is represented by a static specification plus an analyzable code artifact more secure? And how would anyone analyze such possibly complex artifacts for embedded "time-released" attacks that only fire on a particular input?

Our reading of how these fit together: consideration 2 and OP 7.10's first direction are the same dependency seen from two sides. Verification tools need a specification; the specification is exactly what the developer gave up writing; so someone or something trusted has to produce it per task. Consideration 4 is the hopeful version: turn the agent's plan into a fixed artifact first, then analyze it like code. The report flags that this only moves the question to whether the artifact can hide behavior that analysis misses.

A good answer to OP 7.11 would have to fit inside the agent's latency budget, scale its effort with the havoc perimeter (light for the calendar app, heavy for the planner), and say clearly where the specification it checks against comes from.

Before you ship an agent, write its havoc version: replace every model call with "anything" and read what the code still allows. If what is left is a bounded set of side effects you can live with, you have a perimeter. If what is left is exec(*), your security rests entirely on the model and whatever monitor sits around it.
